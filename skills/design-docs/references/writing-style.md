# 設計書の文体・内容・メタデータ

## 読者と文書型

各文書に主読者を一つ設定する。複数の目的を一つの文書へ詰め込まず、入口から必要な詳細へリンクする。

| 文書型 | 読者の問い | 構成の中心 |
|---|---|---|
| 要件 | 何を満たすか | 目的、範囲、要件、品質、制約、受入条件 |
| アーキテクチャ | 全体をどう分けるか | 関心事、境界、ビュー、制約、判断 |
| 詳細設計 | どのように動くか | 入出力、処理、状態、失敗、認可、検証 |
| 契約 | 何を保証するか | schema、互換性、エラー、例、制約 |
| 運用 | どう動かし、戻すか | 前提、手順、判断、失敗、復旧、連絡 |
| ADR | なぜこの案か | 背景、選択肢、判断、結果、トレードオフ |

## 基本文体

- 日本語を基本にする。固有のAPI名、コマンド、標準用語は原語を併記する。
- 一文一義にし、主語・動作・対象・条件を近づける。
- 能動態を優先し、責任主体を隠さない。
- 「適切に」「高速に」「十分に」「ユーザーフレンドリー」など検証不能な表現を避ける。
- 要件は一文一要件にし、安定したIDと検証方法を付ける。
- 手順は番号付き、比較は表、選択は条件付き箇条書きにする。
- 事実、推測、仮定、未決定事項を見出しやラベルで分ける。
- 同じ概念には同じ用語を使い、略語は最初に定義する。
- 各節の冒頭に「この節で分かること」を一文で置く。

## 規範語

文書の先頭で意味を固定する。日本語文書では、次の対応を採用する。

| 表現 | 意味 |
|---|---|
| `MUST` / 「〜しなければならない」 | 例外なく満たす。検証方法が必須 |
| `MUST NOT` / 「〜してはならない」 | 禁止。違反時の扱いを記録 |
| `SHOULD` / 「〜することが望ましい」 | 原則満たす。外す場合は理由を記録 |
| `MAY` / 「〜してもよい」 | 任意。採否を実装・運用で決める |

## 標準の節

文書型に応じて不要な節は省いてよい。ただし、適用範囲、前提、制約、検証、関連ID、変更履歴は隠さない。

1. 目的と結論
2. 対象読者
3. 対象範囲・非対象範囲
4. 前提・制約・用語
5. 本文（仕様、構造、処理、判断）
6. 失敗・例外・セキュリティ境界
7. 検証方法と受入条件
8. 関連要件・設計・ADR・図・テスト
9. 未決事項・再評価条件
10. 変更履歴・参照元

## front matterと版

front matterの項目はプロジェクト内で固定する。下記は最小例であり、不要な項目は増やさず、必要な項目は省略しない。

```yaml
---
id: ARCH-001
type: architecture
title: システムアーキテクチャ
status: draft
source_of_truth: true
doc_version: 0.1.0
product_version: 1.0.0
created: 2026-08-09
updated: 2026-08-09
applies_to: [core]
related_requirements: [REQ-F-001, REQ-NFR-001]
related_designs: []
related_diagrams: [DG-C4-001]
related_adrs: [ADR-001]
related_tests: []
---
```

- `doc_version` は文書の変更、`product_version` は対象プロダクトの版を表す。
- 破壊的な意味変更はmajor、内容追加はminor、誤字やリンク修正はpatchとする。
- `status` は `draft`、`planned`、`in-review`、`approved`、`implemented`、`deprecated`、`superseded` から選ぶ。`planned` は図仕様など作図前の成果物に限り、通常の設計書には使わない。`完了`や`未着手`は使わない。
- 変更履歴は本文または専用Changelogへ残し、いつ・なぜ・何に影響したかを示す。

front matterの関連項目は `related_requirements`、`related_designs`、`related_diagrams`、`related_adrs`、`related_tests` に統一する。`requirements`、`diagrams`、`adrs` の短縮名を同じ文書体系で混在させない。差分文書だけは、これに加えて `variant_id`、`base_document`、`base_version` を持つ。図仕様は専用の `diagram_id`、`type`、`source_file`、`rendered_file` を持つが、関連IDのキーは共通キーを使う。

front matterの優先順位は、(1) このSkillの共通schema、(2) 文書種別の追加キー、(3) プロダクト固有の追加キーとする。プロダクト固有キーで共通キーの意味を上書きしてはならない。キーを省略する場合は、文書種別の適用判定と省略理由を文書カタログへ記録する。

## 設計書と実装の境界

- 要件書は「何を満たすか」、設計書は「どう構成するか」、ADRは「なぜその選択か」を主に記述する。
- 事実でない技術選定、性能値、法令適合、セキュリティ保証を作らない。
- 機密情報、API key、private key、実データを設計書や例に入れない。
