# 編集可能なPowerPoint構成図

## 基本方針

構成図は「きれいな絵」ではなく、読者が一つの設計上の問いに答えられる説明資料として作る。最初に目的・読者・抽象度・範囲を決め、必要な情報だけを載せる。PowerPointで編集しやすいことを優先し、ノード、境界、ラベル、経路はネイティブ図形・テキスト・line shapeを使う。図全体をPNG/SVG一枚に焼き付けない。

## 実行手順

1. 入力資料、既存図、設計書、README、コード、ユーザー指定の前提を読む。
2. 次の入力を確定する。分からない重要情報は推測せず、質問する。
   - 図の目的と想定読者
   - 図種（context / container / component / deployment / network / data-flow / sequence）
   - 対象範囲、外部システム、信頼境界、ネットワーク境界
   - ノード、データ/通信経路、方向、プロトコル、同期/非同期、認証・暗号化
   - 出力サイズ、既存テンプレート、ブランド、納品先
3. [図解の作法](references/diagram-conventions.md)と[矢印意味の契約](references/arrow-semantics.md)から、図種・抽象度・レイアウト・関係語彙を選ぶ。1枚に複数の抽象度を混在させず、必要なら context → container → focused flow の複数スライドに分ける。
4. 先に図の仕様をJSONで作り、`scripts/check_diagram_spec.py --layout --semantics`で検証する。ノードID、境界、エッジ、ラベル、凡例に加えて、座標、サイズ、直交配線、交差、ラベル衝突、密度、矢印の意味と線種の一致を機械的に確認してから描画する。経路ラベルは矢印から0.32インチ以内、親子でない境界は0.12インチ以上離し、コネクタが境界外周をなぞらないことも必須とする。
5. [PPTX作成手順](references/pptx-workflow.md)に従い、16:9の安全領域とグリッドを先に固定する。左右または上下の主方向を一つに決め、整列・均等配置・余白・線の交差回避を行う。箱を斜めに並べたり、長い文言を入れるためだけに縦長にしたりしない。
6. アイコンは[アイコンポリシー](references/icon-policy.md)と[資産の出典](references/icon-sources.md)に従う。標準は`icon-first`で、`assets/icons/manifest.json`から意味のあるSVGを解決し、アイコンを主役、ラベルを補足にする。一般概念は`generic.*`、実在するAWS/Azure/Google Cloud製品は`provider`を指定した公式アイコンだけを使う。未収集アイコンは空箱にせず、意味の近い汎用アイコンへフォールバックして解決結果を残す。
7. タイトル、図の目的/範囲、凡例、更新日・版・出典を入れる。情報量が多いときはメタデータをノートまたはフッターへ移し、キャンバスを圧迫しない。
8. PPTXを保存し、`scripts/validate_pptx.py`を実行する。PowerPointまたはLibreOfficeがあれば実ファイルを開いて確認する。利用できない場合でも、`scripts/render_preview.cjs`で同じ仕様JSONからSVG/PNGレビュー画像を作り、`scripts/visual_qa.py`でコネクタのノード貫通、文字・線・ゾーン見出し・凡例の重なりを検査する。プレビュー画像を見たことと、PowerPoint本体を目視確認したことは別に報告する。
9. `scripts/run_visual_fixtures.py`で、ネットワーク経路、ゾーン配置、セキュリティ境界、データフロー、意図的に崩したケースを通す。1枚の作成・評価は`scripts/review_diagram.py`で、仕様検証、visual QA、画像生成、PPTX構造検証を一括実行する。失敗ケースが検知されたら、箱の追加ではなくラベル短縮、ノード間隔の確保、経路の直交化、境界間の余白、専用ラベルレーン、凡例化、詳細図への分割を優先する。
10. 最終成果物として、PPTX、元の図仕様JSON、使用アイコンの出典/許諾メモ、検証結果を同じ納品フォルダに置く。事実不明の箇所は`要確認`として図中または付属メモに残す。

## 図の作り方のルール

- 1スライド1メッセージを基本にする。ノードが多い場合は分割し、1枚に詰め込まない。
- 標準は16:9、16:9の安全領域、0.25インチ程度のグリッドとする。座標はグリッドに吸着し、同じ層の中心線を揃える。
- 通常の箱は横長〜正方形（高さ/幅1.45以下）とし、縦長化で文章を押し込まない。長い説明は短い役割名、最大2行の補助ラベル、凡例、注記、または別スライドへ逃がす。
- 左→右の図では主経路を同じ水平線に並べ、上→下の図では同じ垂直線に並べる。意図的な補助層だけを`allow_staggered`として明示する。
- コネクタは標準で水平・垂直の直交配線とする。斜め線、曲線、無意味な折れ、ノードを横切る線は失敗として修正する。交差が避けられない場合は経路を変えるか、図を分割する。
- 同じ意味のノードは同じサイズ・形・線幅・文字サイズにする。製品ロゴだけを大きくして抽象度を混在させない。
- まず全体を一目で読める概要にし、複雑な詳細はcontainer/component、focused flow、deploymentなどに分ける。図の利用者が説明なしで理解できるかを独立にレビューする。
- 同じ種類の要素は同じ色、形、線幅、文字サイズで表す。色だけに意味を持たせず、形・線種・ラベルも併用する。
- 通信・依存関係は原則として単方向矢印にする。双方向なら往復を2本に分け、各方向へ意味のあるラベルを付ける。
- 線の意味（同期/非同期、データ/制御、信頼境界など）を変えるなら、凡例を必ず置く。意味のない装飾線を増やさない。
- ノード名だけでなく、必要に応じて役割、製品名、プロトコル、データ種別を近くに置く。略語は最初に展開する。
- 境界は背景の薄い塗り、枠、見出しのいずれかで表し、境界をまたぐ経路と境界内の経路を区別する。
- draw.io風の標準は、薄いグレーのキャンバス、淡いゾーン塗り、意味のある大きなアイコン、近接した短いラベル、下端の横一列の凡例である。ノードを四角と文字だけで表現したり、0.26インチ程度の小さなバッジに押し込んだりしない。過剰な影・グラデーション・縦積み凡例は避ける。
- `relation`を省略して線種から意味を推測させない。データフロー、依存、制御、監視、メッセージ、応答、関連を[矢印意味の契約](references/arrow-semantics.md)から選び、`from`→`to`を自然な一文として読めるラベルにする。
- 公式ブランドアイコンを切り抜き、反転、回転、引き伸ばし、勝手な色変更にしない。汎用の「API」「サーバー」「DB」などをブランドロゴで表さない。
- 公式ブランドアイコンはprovider/productが実在する場合だけ使い、製品名をアイコンの近くへ置く。自社サービスをベンダーアイコンで表さない。
- ノードとテキストは別々に編集できるようにする。アイコン画像を使う場合も、製品名・役割は別のテキストボックスにする。
- 交差する線、重なるラベル、極端に小さい文字、過度な影や3D効果を避ける。印刷・白黒表示でも区別できるようにする。

## 実装手段の選択

1. 既存の会社テンプレートがある場合はそれを優先する。
2. プログラム生成なら、標準の`scripts/create_drawio_pptx.cjs`とPptxGenJSを使う。PptxGenJSの例は[公式リポジトリ](https://github.com/gitbrent/PptxGenJS)を参照する。手書きの`p:cxnSp`や負のtransformを含むPresentationMLは標準経路に使わない。
3. どのライブラリを使っても、編集可能なテキスト、図形、線、画像をスライド上の別オブジェクトとして出力する。最終PPTXだけでなく、再生成可能な仕様/ソースを保存する。
4. ライブラリがない場合は、利用可能な環境を確認してからローカル依存を追加するか、PowerPointで編集可能な元テンプレートを作る。依存追加や外部アイコン取得は、利用者に影響する範囲を明示する。

## リソース

- `references/diagram-conventions.md`: 図種、抽象度、レイアウト、矢印、凡例、アクセシビリティ。
- `references/arrow-semantics.md`: データフロー、依存、制御、監視、メッセージ、応答の向き・線種・ラベル契約。
- `references/pptx-workflow.md`: PPTXオブジェクト、編集性、生成ライブラリ、検証。
- `references/icon-policy.md`: 同梱中立アイコン、ベンダー公式アイコン、ライセンスと更新。
- `references/icon-sources.md`: 同梱資産の出典、取得版、利用条件、フォールバックルール。
- `references/output-checklist.md`: 納品前レビューのチェックリスト。
- `assets/icons/catalog.json`: スキル内の中立SVGアイコン一覧。
- `assets/icons/manifest.json`: generic/providerアイコンの解決、出典、SHA-256、権利クラス。
- `scripts/check_diagram_spec.py`: 図仕様JSONの構造検証。
- `scripts/semantic_policy.py`: relationと線種・矢印方向・ラベルの検証。
- `scripts/create_drawio_pptx.cjs`: PptxGenJSによるdraw.io風・編集可能PPTXの標準ジェネレーター。
- `scripts/render_preview.cjs`: 仕様JSONと同じ座標・アイコンmanifestから再現可能なSVG/PNGレビュー画像を生成する。
- `scripts/visual_qa.py`: 画像レビュー前に、ノード・ノード内文字・経路ラベル・ゾーン見出し・コネクタ・凡例の重なりを機械検査する。
- `scripts/review_diagram.py`: 仕様検証、visual QA、プレビュー生成、PPTX構造検証を一括実行する。
- `scripts/layout_policy.py`: 16:9安全領域、グリッド、箱の比率、整列、直交配線、交差、ラベル衝突、密度の検証。
- `scripts/run_visual_fixtures.py`: 想定依頼から作った複数の日本語フィクスチャと、編集可能PPTXの構造検証。
- `scripts/validate_pptx.py`: PPTXが画像一枚だけになっていないかを含むOOXML構造検証。
- `scripts/validate_icon_manifest.py`: アイコンファイル、SHA-256、公式出典メタデータの検証。
- `examples/README.md`: 図種別ごとのサンプル仕様、再生成・検証手順。
- `examples/specs/`: コンテナ、ネットワーク／セキュリティ、データフロー、配置の架空サンプルJSON。
- `examples/pptx/`: 上記仕様から生成する編集可能なPPTXサンプル（生成物はgitignore対象）。
- `scripts/package.json` / `scripts/package-lock.json`: PptxGenJSの再現可能なローカル依存。

## 完了条件

- 読者、目的、範囲、図種、抽象度が明示されている。
- 主要なノードと経路が事実に基づき、方向・関係・境界・凡例が読み取れる。
- ノード、ラベル、境界、経路をPowerPointで個別に移動・編集できる。
- アイコンは内容に適合し、アイコンがノードの主役として読め、製品名/役割が近くにあり、利用条件・出典が確認できる。
- `check_diagram_spec.py`、`validate_pptx.py`、OOXML relationship/transform検査、可能な場合のOffice/LibreOffice目視確認が完了している。
- `visual_qa.py`が衝突エラーなしで通り、SVG/PNGレビュー画像を確認済みである。Office/LibreOfficeの目視確認をしていない場合は、その制約を明記する。
- 斜め配置、縦長箱、線の交差、ラベル衝突、過密ケースを検知するフィクスチャテストが完了している。
- `examples/` のサンプル図は仕様JSONから再生成でき、構造検証結果と目視確認の制約を報告している。
- 不明点、仮置き、要確認事項を隠していない。
