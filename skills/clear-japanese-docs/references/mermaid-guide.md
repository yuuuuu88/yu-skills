# Mermaidの使い方

## 図を使う条件

Mermaidは装飾ではなく、関係を理解するために使う。

- 手順や分岐が文章だけでは追いにくい。
- 複数の登場人物やサービスのやり取りがある。
- 状態、データ、階層、時系列を説明する。
- 図にすると本文を短く正確にできる。

単純な1〜2手順だけの場合や、図を入れる方が本文を長くする場合は省く。

## 図種の選び方

| 図種 | 使う場面 |
|---|---|
| flowchart | 手順、分岐、意思決定 |
| sequenceDiagram | 人・サービス間のやり取り |
| stateDiagram-v2 | 状態と状態遷移 |
| erDiagram | データやエンティティの関係 |
| mindmap | 概念や階層 |
| timeline | 出来事や変更の時系列 |
| gantt | 作業計画や期間 |

図の前後に、図が何を示すかを1〜2文で説明する。図1つにつき主題を1つに絞る。

## 読みやすさのルール

- ノードを増やしすぎない。
- ノード名は短くする。
- 矢印の向きに意味を持たせる。
- 分岐には条件を書く。
- 略語だけのラベルを避ける。
- 本文と図の内容を一致させる。
- 対応する図種ではaccTitleとaccDescrを付ける。
- 公式構文を参照し、利用可能ならレンダリングして確認する。

## 例

~~~mermaid
flowchart TD
    accTitle: 文書作成の流れ
    accDescr: 入力文書を読者向けの説明へ整理する流れ
    A[入力文書を読む] --> B[読者と目的を整理]
    B --> C{図が理解を助けるか}
    C -->|はい| D[Mermaid図を追加]
    C -->|いいえ| E[図を追加しない]
~~~

## 検証

- Mermaidのコードブロックで囲む。
- 図の宣言が図種に合っているか確認する。
- ノード、矢印、分岐、終点の対応を確認する。
- endなど構文に影響する文字列は公式仕様で確認する。
- レンダラーがない場合も、コードの構造と本文の対応を手動確認する。
